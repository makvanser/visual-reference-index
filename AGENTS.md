# AGENTS.md

## Project purpose

This repository is a visual reference catalogue for website screenshots. The application must remain a neutral, fast working library: the references are the visual focus, while the interface provides filtering, search, modal inspection, source galleries and Markdown export.

## Stack and commands

- React 19 and Vite 8.
- Metadata is stored in JSON; there is no backend or database.
- `npm ci` — install the locked dependency tree.
- `npm run dev` — start the local catalogue.
- `npm run scan` — sync `screens/` to `public/screens/` and update the pending-analysis queue.
- `npm run validate` — validate IDs, families, colors, media paths and family counts.
- `npm test` — run interaction and export tests.
- `npm run build` — create the production bundle.

Before handing off a change, run `npm test`, `npm run scan`, `npm run validate` and `npm run build` unless the requested work is explicitly read-only.

## Data architecture

- `screens/` contains canonical source screenshots. Never delete, rewrite or rename them without explicit user approval.
- `public/screens/` is generated by the scan workflow, served by Vite and intentionally ignored by Git.
- `public/materials/<reference-id>/` contains additional verified images and videos from cited sources.
- `data/references.json` is the source of truth for reference analysis.
- `data/families.json` is the source of truth for style-family descriptions and counts.
- `data/pending-analysis.json` is a generated queue, not a place for invented metadata.
- `src/App.jsx` consumes the JSON generically. Do not hardcode individual references in components.

## Adding a reference

1. Inspect every supplied image and the cited source before editing metadata.
2. Put the unchanged primary screenshot in `screens/` and run `npm run scan`.
3. Reuse an existing family when the composition and visual language match. Create a family only when the reference is genuinely distinct.
4. Add one complete entry to `data/references.json`; keep IDs sequential and stable.
5. Store cited source media locally under `public/materials/<reference-id>/` and list every file in `source_materials`.
6. Update the selected family's `reference_count` and, only when warranted, its shared palette or principles.
7. Add or update tests for catalogue totals, material totals, source links and Markdown export.
8. Run the full verification command set.

## Analysis rules

- Never invent site names, exact fonts, awards, scores, technologies or interactions.
- Use `null` for an unavailable numeric award score; the UI and Markdown export intentionally omit it.
- Mark inferred visual values with an appropriate confidence level.
- Keep the primary palette to 3–6 meaningful colors.
- Prefer 3–7 tags that explain what visually sustains the design.
- Keep family names emergent from the collection; do not create one category per screenshot.
- Preserve source URLs and distinguish verified facts from visual inference in `notes`.

## UI constraints

- Maintain the restrained editorial appearance: warm white canvas, dark typography, thin rules, generous whitespace and no gradients or dashboard styling.
- Preserve responsive behavior, keyboard modal navigation, URL-synced filters/search and per-card Markdown download.
- Route local media through the Vite base URL helper so GitHub Pages project paths continue to work.
- Do not crop source previews destructively or modify original images.

## Git and deployment

- GitHub Pages is deployed by `.github/workflows/deploy-pages.yml` from `main`.
- The project-site base path is `/visual-reference-index/` and is supplied during the Pages build.
- Do not commit `node_modules/`, `dist/`, generated `public/screens/`, secrets or root-level duplicate screenshots.
- Preserve unrelated user changes. Do not reset, force-push, rewrite history or delete assets unless the user explicitly requests it.
